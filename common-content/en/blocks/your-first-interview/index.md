Throughout ITP you have now had experience building projects, giving demos, and now it's time to put it all together. During today's class, you will take part in a very short interview where you can practice proving yourself to an interviewer during a discussion about a recent project you built.

Interviews can be stressful, especially if you have not done one before. That's why we're doing one now! There is no pass or fail here, and you can share your experiences with the rest of the class.

Being able to answer questions in an interview setting is a vital skill for employability, you won't get a job without this! It will also help to build on the earlier "Answering demo questions" workshop, and improve your ability to communicate about code with colleagues. This also acts as some practice in advance of the checkpoint that follows ITP.

The key to interviews is being able to convince the interviewer that you fully understand the code in a project. We want to practice with a decent sized project, so here are some of the ones you could use:

## How the interview will go
For trainees, here's how the interview will go, it should last no longer than 10 minutes:
* As part of your backlog, you shared the project to talk about in a slack thread earlier in the week
* The interviewer will ask you to introduce yourself in 30 seconds, like you have been practising during the "Introduce Yourself!" energisers at the start of classes
* For up to 5 minutes, answer questions the interviewer has about the code you have written
* At the end, the interviewer will give you some brief feedback on how things went


## Advice for the facilitator
The goal is to give everyone in the group experience with a short one on one interview. You will need to do this one at a time, so you will need to do organise this in parallel while the trainees are working on their group work tasks or self study. If you have multiple volunteers or staff in a large class, share the interviews out.

Here are some tips:
* Check the slack before class, to familiarise yourself with the project each trainee wants to talk about
* Ask the trainee to open up the code on their machine, and discuss it there, don't take over controlling their machine
* We don't want to give trainees undue stress, so keep to the time limits suggested.
* If a trainee clearly doesn't understand you can try to prompt them in the right direction, but if they really don't understand go easy on them rather than grilling them too intensely
* One goal is to see if a trainee can convince you they understood code, see the pointers below
* You can use any question you feel is appropriate, but try to focus on more complex, non-trivial, or interesting parts of code
* When you're giving feedback at the end, do so from the viewpoint of an employer


## Evidence of good understanding
Things for the interviewer to praise and look for.
Trainees should try to aim to show they can:
* Give a high level overview of a function after a quick read through
* Navigate through a codebase, knowing where everything is
* Explain the theory or usage behind JavaScript APIs like DOM, listeners, regexps, fetch
* Offer explanations of code at different levels, e.g. user-facing considerations, developer-facing considerations
* Explain choices / alternative approaches / trade-offs


## Evidence of poor understanding
If interviewers spot these, it could be a sign a trainee doesn't understand code.
Trainees should practice and aim to avoid these if possible:
* Being unsure where different parts of code are in a codebase, or having difficulty navigating a project
* Spending too much time reading code line by line, and being unable to give a high level overview
* Using JavaScript APIs while being unable to explain how they work
* Knowing jargon and buzzwords but being unable to explain code with simple language
* Confusion over complex syntax like ternary, complex boolean, destructuring expressions, higher order functions
* Can't answer questions about code written by a teammate in a group project
